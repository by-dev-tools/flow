### FB-0108 — Fix the interface, not the call sites — and a fix that looks correct is not verified until you attack it

**Date:** 2026-09-12
**Source:** user direction (orchestrator dispatch of the `add-entry` shell-injection fast follow, and the design note on what "interface fix" has to mean) + the measured lesson from #148's own first attempt

**What was said:** `/flow:security-review` on #148 found that `manifest-triage.py add-entry` takes `--finding`/`--resolution` as raw argv while every producer site in `ship/SKILL.md` instructs the executing agent to compose that command with attacker-influenceable text embedded in it (a plan-authored Spec-walk criterion, a reviewer finding, a status doc's stale line). #148 shipped a narrow per-site fix and the human dispatched the systemic half as a fast follow, stating the requirement precisely: *"The narrow fix made the CURRENT call sites safe by quoting them. The interface fix is supposed to make the NEXT call site safe by construction, so a future caller cannot reintroduce the injection by passing raw argv. If what you have built still accepts raw argv as an equal-status path, it has not done that job — the unsafe door has to be closed, not merely joined by a safe one."* The justification given was this repo's own scar: `/flow:doctor` defaulted doc-path slots to `core-docs/` while the schema and 16 other call sites said `dev-docs/` (FB-0098) — one contract, many runtimes, held together by nothing but author memory.

Separately and independently, #148's *first* attempt at the narrow fix used a quoted heredoc (`<<'FLOWEOF'`) to capture the criterion. That genuinely closes the quote, backtick and `$(...)` vectors, reads as correct, and would pass review. An adversarial re-check found it is not: the delimiter is a fixed, guessable string, so plan text containing a bare `FLOWEOF` line terminates the heredoc early and hands everything after it to the shell as commands. The worker's stated lesson was **"reading the code is not the same as running it"** — it found the hole only by attacking its own fix with crafted payloads. That refutation arrived while the fast follow's plan was at its own plan gate, and it invalidated three successive candidate designs in that plan (two heredoc variants and a separator-sentinel variant), all of which had survived `/flow:critique-plan` on their internal coherence because coherence is not the property at issue.

**Synthesized rule:**

1. **A safety fix applied per-call-site is a convention; only an interface change is a fix.** The test is not "are the current call sites safe" but "can the next author reintroduce the hazard without noticing." If the unsafe path remains callable, the answer is yes and the work is not done — so the unsafe door must be *closed*, not joined by a safe alternative. Concretely: remove the unsafe parameter rather than deprecate it, and keep a named rejection arm that exits non-zero with the replacement spelled out, so a stale copy-paste from an old doc gets taught the new spelling instead of a generic usage dump. A rejection arm is not an equal-status path — it has no flag, env var or fallback that reaches the old behavior. Corollary for reviewers: "N call sites are now correct" and "the class is closed" are different claims, and only the second one survives a new author.
2. **Every text-based boundary can appear in the text.** Heredoc delimiters, separator sentinels, fences and magic markers all fail the same way and for the same reason, so refuting one refutes all of them — do not spend a round rediscovering the next variant. The only safe channels are ones the interpreter never parses: a file path the untrusted bytes are written to out-of-band (here, by the agent's Write tool rather than by any shell construct), or a value passed through a non-textual channel (`jq -n --arg`). When choosing a mechanism, ask what string, appearing inside the payload, would break it; if such a string exists, the mechanism is already refuted.
3. **A fix that looks correct is not verified until you attack it, with payloads designed against the specific mechanism you chose.** Reading the code is not running it. Generic "does it round-trip" tests cannot generate the payload that breaks a design, because they are not adversarial to the design — they are adversarial to nothing. So the payload set must be mechanism-specific: a delimiter scheme needs a payload containing the delimiter; a file path needs a symlink and a traversal attempt; a parser needs its own separator. Name the payloads in the PR body so the next reader sees what was actually tried rather than trusting the word "verified" — and per FB-0004, assert on what a real breach would emit (the leaked content), never on a proxy like an exit code or a message string.

**Applies to:** `plugins/flow/skills/ship/lib/manifest-triage.py` (`add-entry`/`record-attempt`/`waive` input path — the concrete instance); `plugins/flow/skills/ship/SKILL.md` producer sites; `.claude/rules/general.md` § Consistency discipline (FB-0010 — this is the fan-out/author-memory class, one altitude up, at an interface rather than a value); FB-0098 (`core-docs/` default — the prior instance of one contract with many runtimes); FB-0055 (prefer the durable structural fix over an author-memory convention — the same human resolving the same fork the same way); FB-0004 (assert on what would leak, not on a proxy — governs rule 3's payloads); any future flow CLI that accepts model-composed free text.
