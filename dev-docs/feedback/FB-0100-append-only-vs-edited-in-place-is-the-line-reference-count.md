### FB-0100 — The line is APPEND-ONLY vs EDITED-IN-PLACE, not "prose vs machine-input"; and reference COUNT is not COUPLING

**Date:** 2026-09-06
**Source:** user direction (framing correction during the doc-fragmentation design session) + a defect the same session found in its own conclusion

**What was said.** The design session that decided to fragment flow's append-only docs initially framed the split as "prose docs vs machine-input docs" — fragment the ones nothing parses, leave the ones a parser reads. The user corrected the framing: **the load-bearing distinction is APPEND-ONLY vs EDITED-IN-PLACE.** That reclassification is not cosmetic. It moves `feedback.md` from the "don't touch" side to the "movable" side — and `feedback.md` is where *all three* of the repo's observed FB-number collisions came from, so the original framing would have excluded the single highest-value target.

The session also produced a generalizable measurement lesson: **reference COUNT is not COUPLING.** `feedbackPath` has 17 references across the repo, which reads as "deeply coupled, do not move." Almost all of them merely *name* the file — a slot table row, a "see also" citation, a default in a fallback chain. Only a structural parser is a true blocker, and there were none for the three append-only docs (`extract-criteria.py` / `walk_extract.py` parse the **plan** doc only; verified, not assumed).

**Synthesized rule (1) — classify by write pattern, not by consumer.** Before deciding whether a document can change shape, ask *how it is written*, not *who reads it*. Append-only documents (every change adds a new entry at one insertion point: history, feedback, changelog) are the ones that generate merge conflicts, and they are the ones one-file-per-entry fixes. Edited-in-place documents (plan, roadmap, spec) are rewritten in the middle, their single-document shape is what makes them readable as current state, and fragmenting them buys nothing. "Is it prose?" is the wrong question and gives the wrong answer.

**Synthesized rule (2) — count references, then classify them; never stop at the count.** A high reference count is a prompt to look, not a verdict. Sort every reference into: (a) **structural** — something parses the file's internal shape, a real blocker; (b) **existence-testing** — something branches on whether the path resolves, a real blocker *and the one that hides*; (c) **nominal** — the path is merely mentioned, a rename. Only (a) and (b) constrain the decision. Reporting "17 references, therefore coupled" is an unverified claim wearing a number.

**Synthesized rule (3) — existence-testing readers are a third category, and they fail SILENTLY.** This is the defect the session found in its own approved conclusion, which had claimed "ZERO parser changes." True for structural parsers; false overall. `[ -f "$X" ]` is **false on a directory**, so the moment a slot points at a fragmented doc, every `[ -f ]` reader reports "(no doc)" and runs without its context — fail-open, no error, *indistinguishable from a project that legitimately has none*. Five surfaces would have broken here: three reviewer preludes on `feedbackPath`, `/flow:land`'s CHANGELOG-currency block on `changelogPath` (worst of the four — the whole check became a silent no-op), and `referenceGlob`, which would have dropped the entire FB corpus out of `/flow:critique-plan`'s reference set *without firing the FB-0082 zero-resolution warning*, because the other reference docs still resolved. Five more sites carried the identical latent bug on slots this change did not repoint.

The rule: **when a path's shape changes, grep for existence tests, not just for parsers.** And per `.claude/rules/general.md` (Consistency discipline, item 1), pair every `|| echo "(no ...)"` fallback with a loud branch — a silent fallback makes a misconfiguration look exactly like an empty set, which is precisely how FB-0082 shipped and went unnoticed. Fixed here by hoisting all doc-slot resolution into one shared `plugins/flow/lib/resolve-doc-slot.sh` with five explicit states, three of them loud.

**Applies to:** any change to a `flow.config.json` path slot's shape or location; any "how coupled is this?" assessment; any decision that reports a reference count as evidence. Also the honest caveat on the one quiet state that remains: an *unset* slot resolving to a *default* path that does not exist stays quiet, because that case genuinely is ambiguous with "this project has none." An explicitly **set** slot that resolves to nothing is never quiet again.
