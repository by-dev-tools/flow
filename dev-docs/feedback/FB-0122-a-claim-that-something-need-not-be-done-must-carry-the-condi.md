### FB-0122 — A claim that something need not be done must carry the condition under which it must

**Date:** 2026-09-27
**Source:** user direction, consolidating three instances found in one week (the third measured in the health-tracker workspace, PR #118)

**What was said:** *"This is the third surface in a week where the same discipline was missing, so it goes in as one rule and not three incidents: a claim that something need not be done must carry the condition under which it must."* And on why the existing defence does not reach it: *"`git grep` cannot find a premise that just became false, which is why item 2's grep-first defence does not reach this class."*

**Synthesized rule:**

1. **Every justification for an omitted check must name the condition that would reinstate it.** Not a restatement of why it is omitted today — the *reversal condition*. "No diff condition here, deliberately" states a decision; "no diff condition here, because `sourceFilePatterns` classifies json/yaml/toml as source so a config-driven toggle can never be docs-only — re-read that slot before trusting this" states a decision **plus the fact that would overturn it**. The second survives the world changing; the first silently stops being true.
2. **This class is invisible to grep, which is why it needs its own discipline.** FB-0010 item 2's defence is *grep first, edit second*: when you change a value, find every reference. That works because the **text** changes. Here nothing changes — the comment is byte-identical on the day it becomes false. There is no old value to search for. The only thing that can catch it is the comment itself naming what to re-check, so the next reader re-derives the premise instead of inheriting the conclusion.
3. **The word "deliberately" is load-bearing in the wrong direction.** It signals *someone thought about this*, which is exactly what stops a reader from re-examining it. In the measured instance it had been true when written and was obsoleted **by the very feature it was attached to** — the comment argued a docs-only PR "drafts today anyway (verify-build runs, cannot launch, returns Unknown)", and the toolchain self-skip that shipped alongside it made verify-build never run. Prefer "deliberately, unless X" over "deliberately".
4. **Three instances, one rule.** A `/flow:doctor` `[UNCHECKED]` line must name the mechanism that would make it checkable; a section in `research/orchestrator-field-manual.md` must carry its deletion criterion; and a comment justifying an omitted check must name the premise that reinstates it. Same shape each time: an assertion about what need not be done, with no expiry condition attached.
5. **Severity scales with what the stale premise is load-bearing for.** The `doctor` case mislabels a verdict. This one produced a pull request that **could not be merged through any sanctioned path**: the `toolchain` manifest entry it filed is in `manifest-triage.CHECK_ONLY`, so never waivable-to-ready and never subtracted, while its own re-check could never pass on a diff with no behaviour to build. The skill's remediation told the human to mark the PR ready and merge it themselves — flow instructing the user to bypass flow. So when auditing this class, rank by *what depends on the claim*, not by how wrong the sentence is.

**Applies to:** `plugins/flow/skills/audit-skips/lib/skip-audit-checks.py` (the measured instance); `plugins/flow/skills/verify-build/SKILL.md` § 1.2; `plugins/flow/skills/doctor/SKILL.md` (the `[UNCHECKED]` case, landing separately); `dev-docs/research/orchestrator-field-manual.md` (deletion criteria); `.claude/rules/general.md` § Consistency discipline — this is a sibling to item 2 that item 2's defence cannot reach, and to item 4 (a measurement that can only return "clean"), because an expired premise is an instrument that can only return "no need to look"; FB-0121 (a gate must distinguish "nothing there" from "I could not see" — the same distinction, one layer down); FB-0107 (install lag is why the consumer-side backstop had to stay).
