### FB-0101 — In an ephemeral workspace the source-diversity bar (single-source protection) stops deferring weak signals and starts destroying them; fix the storage, not the bar

**Date:** 2026-09-04
**Source type:** user direction + review feedback (queue-rescue session following the design-md spike, PR #140)

**What was said:** A `/flow:ship-spike` run on a Conductor cloud workspace harvested three flow-generalizable lessons into the contribution queue and correctly reported that the queue was ephemeral. The human had already archived six other workspaces that day without checking their queues. During the rescue the human observed that flow's single-source protection assumes a queue that persists so a second occurrence can pair with the first — and asked whether that bar is simply wrong in this environment.

**Synthesized rule:** Three distinct lessons, all instances of "a guardrail's premise must hold in the environment it actually runs in."

1. **The bar becomes a DELETER, not a filter.** The **source-diversity bar** — also called single-source protection, one mechanism, two names (FB-0010/FB-0056) — says a lone weak signal does not promote — wait for occurrence #2. That is sound **only if the store survives to see occurrence #2**. On an ephemeral host it does not: every record is single-source on first sight, `recurrence_count` is structurally pinned at `1` forever, and `contribution_store.py dedup`'s exit-3/exit-4 recurrence paths are unreachable. So "drop, it's single-source" no longer means *defer* — it means *destroy*, permanently, on first sight. **The bar's entire justification is a deferral it can no longer perform.** Do not respond by lowering the bar: that treats a storage defect as a judgment problem. Fix the storage; the bar is correct wherever its premise holds.

2. **Recurrence is only counted along the axis the store happens to index — a real blind spot.** This exact root cause was already recorded once, a week earlier, in a different subsystem: `dev-docs/history.md` (AB Step 1, 2026-08-27) notes the harness-audit marker file is *"gitignored/per-clone, so under the now-active flow cloud workflow (ephemeral per-PR workspaces) every fresh workspace's first `--audit-due` reports 'due'"*. **Two subsystems, one defect, found independently — that pairing IS the recurrence the bar was waiting for, and the queue cannot represent it** because it dedups on `lesson_hash` within one store. When judging whether a finding is "single-source", check whether the *same root cause* is already recorded against a **different subsystem**; cross-subsystem recurrence counts, and no mechanism will surface it for you.

3. **User-scope persistence predates flow's cloud workflow and was never revisited.** Three stores are affected and they do **not** share a substrate — resist unifying them: the contributions queue is **cross-project** (fixed here by flushing into the PR, ship Step 4c.iv); the harness-audit marker is **flow-repo-only** (git-backed fix, already filed as roadmap AB.1b — deliberately not fixed here); the memory corpus is **per-project** and reads **0/30 on every fresh cloud workspace**, i.e. not degraded but entirely non-functional (routed to roadmap § Exploration, deliberately not fixed here). Forcing one substrate on three different scopes would over-couple them to look tidy.

**Two build-time findings carried forward:**
- **`sanitize_tokens.py` assumes the origin project is not flow.** `known_tokens.json` records the origin slug, so when flow harvests from its *own* repo a full `scrub` rewrites the literal correct path `plugins/flow/skills/general/SKILL.md` into `plugins/<project>/skills/general/SKILL.md` and `project_slug: flow` into `<project>` — degrading the record instead of protecting it. When origin == destination, the project token is a literal, not a leak. Redact the genuinely machine-specific classes (home paths) and leave the rest.
- **Never put unbounded content in a PR body.** A queued record is ~1.6 KB; GitHub caps a PR body at 65,536 chars, so inline records overflow at **~37** — exactly when the queue has accumulated longest. Commit the full artifacts to the branch and put a bounded ~104-byte manifest row in the body (~600 fit). *Measured, not estimated.*

**The orchestrator-seat gap, and why it gets an instruction rather than a mechanism.** Harvest runs only at ship time (Step 4c in `ship`/`ship-spike`), and the orchestrator seat dispatches, reviews and merge-gates but never ships — so **every lesson generated at the coordinating seat is structurally unharvestable**. It gets no new machinery: the queue exists to carry a lesson **across a repo boundary**, and the orchestrator already sits inside a flow checkout with merge rights, so it writes the project's feedback doc (`flow.config.json.feedbackPath`) directly — the queue's own drain destination. A `/flow:harvest` skill would be the queue-management subsystem this feedback explicitly rejects, and the parallel learner FB-0059(f) forbids. **Tradeoff, stated plainly:** orchestrator lessons skip confidence scoring and dedup. That is an acceptable price against today's outcome, which is that they are lost entirely — on this session alone that cost three measurement failures, a capability-claims-expire correction, and an FB-collision pattern.

**Security lesson, found by `/flow:security-review` on this very change (SAFETY).** A store's *scope* is part of its threat model, and changing who reads it changes who it leaks to. The contributions queue is **cross-project by design** — that is what makes it valuable, and FB-0059 says so explicitly. But a mechanism that *publishes* from that queue inherits the cross-project property as a **leak**: an unfiltered flush would commit project A's slug, branches and internal doc paths into project B's possibly-public repo, simply because both drew from one store. **When adding a new reader or exporter to a shared store, re-derive its scope from scratch rather than inheriting the store's.** Three corollaries from the same review: never `git add -f` into a consumer's repo (a gitignore is a stated preference, not an obstacle); text that flows into a marker-delimited region must have the marker vocabulary neutralized, not merely escaped for the surrounding format; and a discovery query that reads content from arbitrary refs (`gh search prs` without `--author`/`--merged`) is an ingestion path, so it needs an authorship constraint before it needs a parser. **Composition is the blind spot:** an export path and an ingestion path were each defensible alone; together they let anyone's PR body become an edit proposal against a public plugin. Four craft lenses missed it; the adversarial pass did not.
