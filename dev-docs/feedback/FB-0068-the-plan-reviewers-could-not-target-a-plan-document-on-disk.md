### FB-0068: The plan reviewers could not target a plan document on disk, and no mechanical check caught Spec-walk checkboxes that name no verification — both surfaced by prompt-referenced dogfooding in a workspace without the plugin installed
**Date:** 2026-07-12
**Source type:** user direction (dogfooding a consumer project → build the missing capability upstream)

**What was said / what happened.** A consumer project accumulated a directory of ~8 queued plan documents (`plans/*.md`) that needed `/flow:critique-plan` + `/flow:audit-plan`. Two gaps surfaced: (1) the reviewers' preprocessor (`extract_session.py --mode plan`) can only extract "the most recent plan" from the live session transcript — there is no way to point them at a plan *file*; (2) the largest defect class across those plans was Spec-walk checkboxes naming no pinning test or verification artifact, which none of the plan-critic's three categories mechanically catches. The dogfooding ran in a **cloud workspace where the plugin was not installed**: the `auditor` / `plan-critic` prompts were applied *by reference* (read from the repo, run via generic subagents), not dispatched through `/flow:*`. The user directed shipping both fixes upstream and explicitly required the change to acknowledge that the skills were not invoked via the plugin, and to make no assumptions that contradict that.

**Synthesized rule.** (a) **A capability gap can be invocation-independent even when discovered through a non-standard invocation.** The missing `--plan-file` input exists whether or not the plugin is installed — the preprocessor simply has no such parameter — so "we found this without dispatching the skill" is a provenance fact for the record, not a caveat that weakens the fix. Write the feedback and the shipped docs to state the provenance plainly and to avoid any claim that the skills ran or misbehaved. (b) **When a defect class is deterministic, mechanize it as an engine feeding the reviewer, not as a new reviewer category** — flow caps the subjective categories (narrow scope beats wide scope); a lint like `walk-pin-lint.py` reports, the critic assigns severity gated on the project's own documented rule, two-citation discipline intact. (c) **A degraded-evidence render must not manufacture findings** — with no transcript, artifact read-status is `UNKNOWN`, never `UNREAD`, so the auditor cannot mint false unverified-recall flags from absence.

**Applies to.** `plugins/flow/scripts/extract_session.py` (the `--plan-file` path + the standalone-review degradation), `plugins/flow/skills/{critique-plan,audit-plan}/SKILL.md` (argument passthrough + the pinning-lint section), `plugins/flow/skills/critique-plan/lib/walk-pin-lint.py`, and the provenance-honesty discipline for any future dogfood-driven upstream change made from a workspace without the plugin installed.

**Queued follow-up (not in this change).** The same prompt-referenced dogfooding produced two candidate reviewer-tuning signals worth an eval fixture later — but they are recorded as candidates, not folded here, because they can't be precisely quoted from the prompt-referenced runs (evidence-backed discipline): (1) a completeness/"no items outside scope" audit verdict that was accepted while two items sat inside the swept scope (a missed-flag on unverifiable-completeness-claims); (2) reviewer-*suggested* spec text that was itself wrong until source-verified (a fold-guidance lesson: verify reviewer-proposed content against source before applying). File as fixtures + a DISAGREE entry when reproduced under an actual `/flow:*` dispatch.
