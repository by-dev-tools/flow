### FB-0113 — An HTML prototype is the first-build medium for mobile too, so the feasibility read becomes the load-bearing guard rather than a nicety

**Date:** 2026-09-16
**Source type:** user direction (Ben, relayed by the orchestrator; resolves `dev-docs/handoffs/d1-prototype-first-gate.md` §9.4, a MEDIUM-confidence assumption explicitly flagged as a human decision)

**What was said:** Asked to choose the prototype medium for D1's gate 1 on non-web surfaces — an HTML proxy, a platform-specific mockup, or web-only for now — Ben chose **HTML prototypes for the first build, for BOTH web and mobile projects.** This is broader than the recommendation he was given (web-only, with mobile deferred until the proxy question was settled).

**Synthesized rule:** On a UI-surface change, the first build is an **HTML prototype regardless of target platform**. The cost that choice accepts is named in the handoff's own risk analysis: *"the gate approves a look that can't be built natively"* — with an HTML proxy standing in for a native surface, infeasibility now surfaces **after** a look has been approved, which is the one thing prototype-first ordering exists to prevent. So the mitigation the roadmap had listed as a nicety becomes **load-bearing and mechanical**: the prototype must carry a **feasibility read**, and it must be *asserted*, not advisory prose.

**How to apply:**
- The feasibility read is **required unless `platform == "web"`** — defined as the complement, never as a list of native platforms. `platform` is an optional slot whose documented default is *unset*, so an enumeration `{ios, android, tauri}` fails open on the configuration an iOS consumer most commonly ships. Unset counts as non-web and fails closed, with both remedies named (set the slot, or declare the block).
- **The content requirement scales with the answer, because the rule is about the medium, not the enum value.** A browser-delivered surface (`platform: web`, or `library`/`none`/`cli`/`tauri` on a project whose UI is a webview) satisfies it with one declaration line: *"Delivery medium: browser — the prototype is the artifact, not a proxy."* A proxied surface needs the full read: a proxy disclosure plus one row per affordance carrying a verdict from the closed set `native-standard | native-custom | expensive | infeasible` and a reason naming the platform mechanism. **flow's own repo is the reason this matters** — `platform: library` with `uiSurface: true`, shipping real browser UI — and a `platform == "web"` exemption alone would have made gate 1 unreachable here.
- `ios` and `android` **cannot** take the one-line exit. Letting an author declare their way out of the only guard §9.4 has would defeat it.
- **Asserted means the gate refuses.** `prototype-gate.py approve` re-runs the contract and writes no approval record when it fails, so a native prototype with no feasibility read cannot reach gate 1 at all. Every non-`native-standard` row is returned in `must_surface[]` and leads the gate-1 message: a look the human cannot afford must not be approved before its price is stated.
