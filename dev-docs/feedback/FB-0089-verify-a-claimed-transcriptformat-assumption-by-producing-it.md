### FB-0089 — Verify a claimed transcript/format assumption by producing it, not by reading the code that assumes it; and a gitignore pattern with no leading slash matches at every depth, not just the root

**Date:** 2026-08-26
**Source:** review feedback (self-discovered during Step 1 of the model-measurement harness build, FB-0089 lineage; surfaced further by `/flow:staff-review`'s altitude lens)

**What was said:** The queued M-harness plan (drafted in an earlier session) assumed subagent usage lives inline in the main session `.jsonl` as `isSidechain: true` records — inferred from `extract_session.py`'s pre-existing skip logic, never independently confirmed. Before building against that assumption, this session spawned a real throwaway subagent and inspected the resulting transcript files directly. The actual shape was different: subagent invocations write to a **sibling file**, `<session-dir>/subagents/agent-<id>.jsonl` with a companion `agent-<id>.meta.json` (same stem, same prefix) naming `agentType`/`toolUseId`/`spawnDepth` — a clean, direct correlation key, no positional-bracketing heuristic needed. The same live inspection also surfaced that assistant JSONL records sharing one `message.id` repeat an *identical* `usage` snapshot 1–4 times (thinking + tool_use content blocks split across records); naive per-record summation would have overcounted tokens by that multiple, silently, with no crash to flag it.

**Synthesized rule:** When a plan's technical approach rests on an assumption about a runtime format or transcript shape, spend one cheap action producing that shape directly (spawn the real thing, inspect the real files) before writing code against an inferred description of it — this is FB-0085's discipline ("verify a mechanism against the runtime, not against its own documentation") applied to *transcript formats specifically*, and it caught two load-bearing corrections a code read alone would have missed: the actual sidecar-file correlation mechanism, and the message.id-repeat overcounting bug. Neither was documented anywhere; both were only visible by looking at real bytes on disk.

**Corollary — a `.gitignore` pattern with a trailing slash and no leading slash matches at every depth, not just the repo root, and git only enforces that against *untracked* files.** Building the harness's dev-tool script, `git add tools/model-measure/*.py` was refused because `.gitignore` blanket-ignores `tools/` ("Local prototypes + diagnostics; not plugin surface"). The first diagnosis was wrong: concluding a file under an ignored path "cannot be tracked," the script was relocated twice chasing a directory name without the string `tools` — first to `dev-docs/tools/model-measure/` (still matched, because the pattern has no leading slash and git-ignore anchoring at any depth is the default), then to `dev-docs/model-measure/` (worked, but then contradicted CLAUDE.md's own "dev-docs/ is dev-tracking only" doctrine — caught by `/flow:staff-review`'s altitude lens). The actual mechanism, found only by checking existing repo precedent instead of reasoning from the ignore rule alone: git's `.gitignore` only blocks adding a **new, currently-untracked** file matching a pattern; a file already in the index is permanently exempt from its own ignore rule, and this repo already proves it three times (`plugins/flow/tools/memory/check.mjs`, two `template/stacks/*/tools/preflight/*`). The fix was `git add -f` once, at the plan-approved, architecturally-correct location — not a relocation. **The transferable rule: before concluding a gitignored path "can't be tracked," check `git check-ignore -v` on an existing repo file at a structurally identical path — if one exists and is tracked, `git add -f` is the answer, not a rename.**

**Applies to:** any future flow-plugin work that reads or reasons about the Claude Code session-transcript format (`tools/model-measure/`, `plugins/flow/scripts/extract_session.py`); the `.gitignore`-vs-`git add -f` lesson generalizes to any new dev-tooling location choice in this repo.
