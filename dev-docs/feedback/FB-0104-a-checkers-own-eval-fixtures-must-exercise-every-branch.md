### FB-0104 — A checker's own eval fixtures must exercise every branch of its logic — and whether an open call changes what SHIPS is what decides if it routes to the human

**Date:** 2026-09-10
**Source:** review feedback (`/flow:critique-plan`, 3 fix rounds on the vacuous-criterion-check plan) + user direction (escalation-boundary correction, orchestrator communication)

**What was said:** Building the vacuous-criterion check (a deterministic heuristic flagging Spec-walk criteria with no observable predicate, e.g. "Rate limiting works correctly"), the first drafted plan listed five "worked negatives" the heuristic must NOT flag. `/flow:critique-plan` caught that none of the five actually exercised the heuristic's AND-NOT escape-hatch branch (`VACUOUS_PREDICATE_RE` matches AND `CONCRETE_SIGNAL_RE` does not) — the predicate regex never matched any of them in the first place, so they were correctly unflagged by construction, not by the mechanism the plan credited. **A vacuous test, inside a vacuous-criterion checker's own fixtures.** Separately, when reporting two open calls from the plan back to the orchestrator, the orchestrator flagged that on a prior PR it had gotten the escalation boundary wrong — routing a documentation-placement question to the human as though it were a behavior question — and asked this session to state the classification explicitly rather than default to escalating. **The same class recurred a third time in the same PR, one layer deeper:** at `/flow:ship`, `/flow:staff-review`'s staff-engineer lens re-ran the exact counter-example the shipped docstring/history/workflow.md cited as proof the check worked (`"Rate limiting works correctly → verify: manual QA"`) and it did NOT flag — the checker's escape hatch treated the repo's own mandatory pin-marker arrow as a specificity signal, so every pinned criterion (the entire real-world population, since every Spec-walk checkbox in this repo is pinned) was structurally unflaggable. The claim had been *written down and read* three times (docstring, history entry, workflow.md) and never once *executed* until staff-review did.

**Synthesized rule:**

1. **A negative test case must be shown to reach the code path it claims to protect, not merely land on the correct side of the final verdict.** It is easy to write five examples that are all correctly unflagged while none of them ever executes the branch of logic that's supposed to be doing the protecting — five different reasons for the same right answer look identical in a pass/fail table. The fix is a worked example chosen specifically to hit the AND-NOT / escape-hatch branch (here: `"Returns a session token and works correctly"` — the trailing clause DOES match the vacuous-predicate regex, and is unflagged ONLY because the concrete-signal escape hatch also fires). Applies beyond this one script: any predicate built as `A AND NOT B` needs at least one fixture where `A` is true and `B` is what saves it — not just fixtures where `A` is false.
2. **Whether an open call changes what SHIPS — behavior, a consumer-visible surface, or a gate's verdict — is the test for whether it routes to the human.** A choice between two closed-vocabulary tokens with no behavioral difference (reusing an existing manifest verb vs. adding an unused one), or a question about where documentation lives, is the agent's to resolve and merely record, not escalate. Escalation is for choices that are one-way doors, carry cost/risk, or where a reasonable person might actually disagree about the *shipped* result — not for every open-ended-sounding question. Stating the classification explicitly ("neither call changes behavior/surface/gate verdict") lets the reader check the judgment instead of trusting it silently.
3. **A documented counter-example is a claim, not a proof, until someone actually executes it.** Writing a worked example into a docstring/history entry/user-facing doc feels like verification because it reads like a test case — but prose doesn't run. The bug here specifically: the pin-marker arrow was added to the escape hatch on the *reasoning* "an arrow points at a concrete artifact," which sounds plausible and is wrong for this repo's actual convention (the arrow separates a claim from its verification *method*, not from a concrete value). Nobody re-ran the cited example against the code until a later, independent review pass did. Generalizes: when a design decision is justified by a specific worked example in prose, that example belongs in the eval suite too, or it is unverified by construction — and re-running it later is not redundant, it's the first time it was actually checked.

**Applies to:** `plugins/flow/skills/verify-build/lib/criterion-specificity.py` + its eval fixture (the concrete instance); `.claude/rules/general.md` "Autonomous work guardrails" (the escalation-boundary rule this generalizes); any future deterministic checker built as a positive-match-minus-escape-hatch predicate; `dev-docs/workflow.md` orchestrator-communication guidance (FB-0092); the `/flow:staff-review` staff-engineer lens (confirms independent execution of a cited example is worth the review pass, not ceremony).
