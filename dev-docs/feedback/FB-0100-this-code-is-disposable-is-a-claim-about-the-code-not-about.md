### FB-0100 — "This code is disposable" is a claim about the code, not about everything downstream of it — scope a skip rationale to exactly what it covers

**Date:** 2026-09-03
**Source type:** user decision at the plan gate (confirmed a recommendation and supplied the argument that made it decisive), plus a scope condition the user refused to let me assume

**What was said.** Dispatched to close `/flow:ship-spike`'s missing skip-legitimacy audit, I asked which of `/flow:security-review`, `/flow:accessibility-review` and `/flow:audit-coverage` should also run in spike mode, flagging accessibility as the genuine judgment call at MEDIUM-HIGH — my own case for it was that spike-mode a11y is bounded in cost, and my counter-case was ship-spike's own stated rationale that reviewing craft on throwaway code is theater. The user confirmed it and supplied a fourth argument I had not made: *"flow is actively moving the human gate ONTO prototypes... If prototypes become the artifact where visual and interaction decisions actually get made, then an accessibility flaw in a prototype does not die with the throwaway code — it propagates into the real PR as an approved pattern. That is the opposite of theater."* And: *"ship-spike's stated 'disposable' rationale is specifically about /simplify and staff-review — code quality on code that gets deleted. It does not extend to the accessibility of a PATTERN. Do not let the existing prose be read as covering more than it says."*

**Synthesized rule.** A skip rationale is scoped to what it literally claims, and inherits nothing. "The code is disposable" licenses skipping reviews *of that code's quality* — and says nothing about the permanence of its commit (a secret survives the code's deletion), nothing about the patterns a human approves while looking at it, and nothing about read-only audits that cost almost nothing. When a rationale is invoked for a stage it was not written for, that is not an extension of the argument, it is a *different, unstated* argument that has to stand on its own. Write the boundary down where the rationale lives, so the next reader cannot quietly widen it — and where the widening would be a silent gate loss, enforce the boundary mechanically rather than in prose (here: the audit engine refuses `spike`/`tiny` as a skip reason for every stage outside a closed two-member allowlist). **Encode the boundary as an allowlist of what the rationale DOES reach, never a denylist of what it doesn't** — this rule's own first implementation was the denylist, and the very next stage added in the same commit silently inherited the hole, as did the behavioral gate. A denylist encodes the stages someone thought of; an allowlist encodes the rule, and anything added later fails closed.

**Second rule, on verifying a scope condition rather than assuming it.** The user made the "spike-only, don't expand into `/flow:ship`" scope decision **conditional** on a fact about my own plan, and refused to let me assume it: *"verify that your pin actually covers the preflight row, not just the rows that existed before... Do not silently pick whichever is easier."* Checking it changed the answer. The drift-pin I had described — mirroring `/flow:ship`'s existing `contract-ship-handoff-*` checks — is a per-file string-presence grep, and would have passed just as green with a stage row the audit engine had never heard of; the asymmetry would have been silent, which by the user's own stated condition argued for the wider scope. Rather than take the wider scope or quietly redefine the condition, I strengthened the pin until it genuinely held (extract both handoffs' stage rows, drive the real engine with them, assert none falls through to `unknown stage`, and pin the ship↔spike row delta as a declared literal), then red-verified both directions. **The rule: when a decision is conditional on a property of your own work, test the property against the artifact rather than against your description of it — a plan's summary of a check is not the check.** **And re-test it after every later edit to the same file:** the strengthened check was subsequently destroyed by an unrelated splice in that harness, leaving `len(rows) >= 7` against 8 rows as the only survivor — so deleting a stage row passed green again, while three dev-docs still asserted the check existed. A verification that satisfied a gate once is not a standing guarantee; only a check that is still executing is.

**Applies to:** any skip/exemption rationale in the workflow docs or a skill's prose (state what it does *not* cover); any future stage added to `/flow:ship-spike` or `/flow:ship` (the row must be a stage `skip-audit-checks.py` recognizes, and `run_scratch_isolation_evals.py`'s `handoff-rows-all-known-to-engine` enforces it); any conditional approval received at a plan gate.
