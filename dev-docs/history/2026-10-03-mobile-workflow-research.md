## 2026-10-03 — Mobile-workflow research: per-gate Mac-app vs iOS-app findings (no code changed)

**Branch:** `conductor/mobile-workflow-investigation` · **SHA:** [this commit] · **Mode:** research (findings-only, no decision made, no shipped skill touched)

**What was done.** Ben asked how the flow workflow could be smoother on a phone, naming two areas (reviewing prototypes/walkthroughs on a phone, using chat on a phone) and expecting more. Dispatched as a research task; mid-task Ben corrected the framing to "one workflow, two clients" — Conductor cloud workspaces driven sometimes from the Mac app, sometimes from the iOS app, with the iOS app able to do less — rather than treating "mobile" as a separate surface. Produced `dev-docs/research/2026-10-mobile-workflow.md`, structured per human gate (prototype gate 1, merge gate, chat hand-offs, cross-client hand-offs), each grounded in the shipped skill code read from `main` and in Conductor's own CLI/changelog.

**Why.** flow's primary user runs the orchestrator/worker loop from both a laptop and a phone; no prior investigation had measured which artifacts a phone client can actually reach.

**Findings (see the doc for full evidence).** Gate 1's prototype (`prototype/SKILL.md` §8) and the merge gate's verify-build walkthrough (`ship/SKILL.md`'s PR-body line) both hand the human a local path — the merge-gate one is a bare path with no protocol, unreachable from the PR on any client, not just mobile. Conductor's own changelog (0.90.0, "Conductor for iOS," dated 2026-10-02) confirms chat + PR merge now work from the phone against cloud workspaces, so the *decision* half of every gate is already portable between clients; the *looking* half is not — no evidence iOS can open an arbitrary HTML artifact, and the Mac-only Browser Preview/Agentation pane has no iOS equivalent. The shared annotation layer (`verify-build/lib/annotation-layer.html`) is touch-compatible at its tap-to-pin core, but every secondary affordance (hover-preview default, modifier-click passthrough, keyboard element-walk) assumes a mouse+keyboard. `conductor preview set` (CLI-confirmed: gated by Conductor sign-in + workspace read access, not public) is named as an unused, available mechanism — the same fix-family as D6's already-measured `file://`-origin bug in this repo.

**Design decisions.** Decided nothing — the brief explicitly asked for findings and ranked, un-built options, not a build. Five questions for Ben are left explicitly OPEN (not answered by guessing); one question (is the `conductor` CLI reachable from an ordinary worker sandbox) was answered `yes` by the orchestrator mid-task from independent evidence (the S0 worker's seven workspaces, plus this session's own CLI runs from a non-orchestrator seat) and closed in the doc rather than left open.

**Technical decisions.** All claims about shipped flow behavior cite the `main` checkout (commit `a250b66`, v1.55.0) rather than this workspace's installed plugin, which was found at v1.29.0 mid-task (provisioning gap, separately being fixed by another worker) and updated here (`claude plugin update flow@flow`) but not restarted — so this very `/flow:ship` run still executes the installed 1.29.0 skill prose, exactly the dogfooding gap `CLAUDE.md` warns about. Noted explicitly rather than silently relied on.

**Tradeoffs discussed.** Ranked options (serving ephemeral artifacts via `conductor preview set`; embedding committed visual-history PNGs as PR-body images; being honest in the hand-off when nothing is reachable; touch-defaulting the annotation layer; a durable glanceable status surface) are stated with cost / consumer impact / security implications but deliberately not chosen or built — Conductor-specific mechanisms must stay optional/best-effort so flow stays project-agnostic for consumers not running inside Conductor.

**Lessons learned.** Hit a live instance of an already-filed trap while shipping this very PR: `/flow:audit-skips` and `/flow:ship` §7a's visual-deliverable gate both flagged this docs-only diff as "visually significant" via the known false positive in `dev-docs/roadmap.md` ("A `**Visual-walk:** N/A` block forces `visual_significant` TRUE") — an unrelated plan block's explicit N/A declaration, not anything in this diff. Routed both to the draft manifest as `human-waive` rather than silently overridden (editing the engine was out of scope) or blindly treated as a real finding about this PR.
