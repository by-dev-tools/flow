## 2026-09-11 — Vacuous-criterion check — close the over-broad-declaration seam audit-coverage leaves (FB-0104, v1.41.0)

**Branch:** `conductor/vacuous-criterion-check-criterion-quality` · **SHA:** [this commit] · **Mode:** feature

**What was done (user-facing).** A new deterministic heuristic, `skills/verify-build/lib/criterion-specificity.py`, runs inside `/flow:verify-build` Step 3 right after `extract-criteria.py` and flags any declared Spec-walk criterion that names no observable predicate — no output, state, value, or error path, just a generic "works" / "correctly" / "as expected" claim (e.g. "Rate limiting works correctly"). Each flagged criterion becomes a `[vacuous-criterion]` entry on the existing draft manifest (a 10th `KIND_COPY` kind in `ship/lib/manifest-triage.py`, `ask` class, reusing `coverage`'s `declare + fence` verb), surfaced through a new additive `metadata.vacuous_criteria_found` field on the verify-build findings buffer and converted by `/flow:ship` Step 2. New eval harness `run_criterion_specificity_evals.py` (34 checks, CI-wired).

**Why.** `/flow:audit-coverage` (PR-2, v1.6.0) closes *under*-declaration — a behavior change with no criterion at all. It leaves a sibling gap open: an agent can dodge coverage by declaring a criterion so vague it plausibly maps to the changed hunk. Coverage sees *a* criterion and stays silent; `/flow:verify-build` then judges the vague criterion PASS against equally vague narration. The two compose to bless a change whose only declared bar is untestably vague — the FB-0047/0048 self-attestation escape, one level up: you can't show a criterion green without a PASS, but you *can* author one so empty that PASS means nothing. Flagged as a named roadmap item at PR-2's own staff-review push-further pass; this PR builds it as specified.

**Design decisions.**
- **Deterministic, never an LLM judgment.** The orchestrator's brief was explicit: a downstream bounded-retry loop needs a mechanical signal to retry against, and judge prose is reward-hackable. A regex heuristic over the extracted criterion text, not a subagent call.
- **Lives in verify-build, not coverage.** The roadmap entry was explicit this is criterion *quality*, verify-build's axis — not criterion *presence*, coverage's axis. Confirmed at the plan gate by reading `audit-coverage/SKILL.md`: it is an LLM-judged fork (`agent: auditor`) checking whether a criterion exists; adding a keyword heuristic there would blur two different kinds of check into one skill.
- **Reuses the `no_plan_fallback` integration shape exactly.** `findings-schema.json` already had a precedent for "a Step-3-derived signal surfaced through `metadata` for `/flow:ship` Step 2 to convert into a manifest entry" (`metadata.no_plan_fallback`). `vacuous_criteria_found` is the same shape, confirmed by reading every `add-entry` call site in the repo (all live in `ship/SKILL.md`, including `toolchain`'s, whose underlying finding originates in a different skill entirely) — manifest writes are centralized in one place by convention, and this follows it rather than inventing a new pattern.
- **Reuses the `declare + fence` verb rather than adding a new one to the closed `VERBS` vocabulary.** The verb only changes classification behavior for `security`/`a11y`/`visual-deliverable`/`toolchain`; for a plain `ask` kind it's inert, so a new verb would be unused vocabulary surface for no behavioral difference. Orchestrator-confirmed at the open-call review.

**Technical decisions / tradeoffs.**
- **Precision over recall, explicitly.** The heuristic is `VACUOUS_PREDICATE_RE` (a small closed vocabulary of generic success verbs, end-anchored to the criterion's trailing clause) AND NOT `CONCRETE_SIGNAL_RE` (a broad escape hatch — any digit, quoted/backticked literal, arrow, or named-observable verb/noun anywhere in the string suppresses the flag). A missed vacuous criterion is an accepted residual; a false `[decision-required]` on a genuinely specific criterion is what gets a gate routed around and stops protecting anything. Documented residual false negatives: "Works differently than before" (real trailing detail defeats the end-anchor — correctly judged more specific than bare "works"), "Error handling works as expected" (contains "error," an escape-hatch word, even though "error handling" alone names no specific error/path).
- **walk-pin-lint.py does not already cover this — confirmed by full read, not assumed.** `skills/critique-plan/lib/walk-pin-lint.py` (FB-0068, SHIPPED) asks, at plan-critique time over the whole plan document, "does this checkbox name a verification *method*" (a test id, or a pin-marker + artifact noun). This new script asks, at extraction time over the active Spec-walk block only, "does the criterion's own text name an observable predicate." They compose rather than overlap, proven with a counter-example each direction: `"Rate limiting works correctly → verify: manual QA"` is PINNED (walk-pin-lint passes) but still VACUOUS (this check fires); `"Retries back off exponentially, capped at 5 attempts"` is UNPINNED (walk-pin-lint flags it) but NOT vacuous (this check does not fire). Recorded in `docs/workflow.md` § 10 so the next reader doesn't re-litigate it.
- **`docs/workflow.md` gets a sentence, not a dedicated paragraph.** Open call at the plan gate, resolved at execution by checking the actual doc: of the 9 pre-existing `KIND_COPY` kinds, only `coverage` and `toolchain` get individual dedicated prose there — the other 7 are covered by the manifest mechanism being explained once, not per-kind. `vacuous-criterion` matches that pattern: one sentence next to `coverage`'s paragraph (its direct sibling), not a new section.

**Lessons learned — the one worth keeping.** `/flow:critique-plan`, run on this plan before execution, caught that the first draft's own eval fixture was itself an instance of the exact defect this checker exists to catch. The plan listed five "worked negatives" — criteria the heuristic must NOT flag — as proof the escape hatch (`CONCRETE_SIGNAL_RE`) worked. None of the five actually exercised it: the vacuous-predicate regex never matched any of them in the first place (none of their trailing clauses were "works"/"correctly"/etc.), so they were correctly unflagged by construction, not by the AND-NOT mechanism the plan credited. **A vacuous test, inside a vacuous-criterion checker's own fixtures** — five different reasons for the same right answer, indistinguishable in a pass/fail table, none of them the reason claimed. Fixed by adding the one case that actually reaches the branch: `"Returns a session token and works correctly"` — its trailing clause DOES match the vacuous-predicate regex, and it is unflagged only because the escape hatch also fires. The eval harness (`run_criterion_specificity_evals.py`) asserts this case explicitly, by name, separate from the general fixture pass, rather than letting it dissolve into the flagged/unflagged set where the distinction would be invisible again. Generalizes beyond this script: any predicate built as `A AND NOT B` needs at least one fixture where `A` is true and `B` is what saves it — not only fixtures where `A` is false. Synthesized as FB-0104 alongside the escalation-boundary lesson from the same session (whether an open call changes what SHIPS is what decides if it routes to a human, not the mere existence of ambiguity).
