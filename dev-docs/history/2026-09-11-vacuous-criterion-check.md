## 2026-09-11 — Vacuous-criterion check — close the over-broad-declaration seam audit-coverage leaves (FB-0104, v1.41.0)

**Branch:** `conductor/vacuous-criterion-check-criterion-quality` · **SHA:** [this commit] · **Mode:** feature

**What was done (user-facing).** A new deterministic heuristic, `skills/verify-build/lib/criterion-specificity.py`, runs inside `/flow:verify-build` Step 3 right after `extract-criteria.py` and flags any declared Spec-walk criterion that names no observable predicate — no output, state, value, or error path, just a generic "works" / "correctly" / "as expected" claim (e.g. "Rate limiting works correctly") — including when that criterion is pinned per this repo's own FB-0068 convention ("`<claim> → verify: <method>`"); pinning is not a specificity signal, and the fix strips the pin annotation before judging the claim underneath it. Each flagged criterion becomes a `[vacuous-criterion]` entry on the existing draft manifest (a 10th `KIND_COPY` kind in `ship/lib/manifest-triage.py`, `ask` class, reusing `coverage`'s `declare + fence` verb), surfaced through a new additive `metadata.vacuous_criteria_found` field on the verify-build findings buffer and converted by `/flow:ship` Step 2. New eval harness `run_criterion_specificity_evals.py` (40 checks, CI-wired).

**Why.** `/flow:audit-coverage` (PR-2, v1.6.0) closes *under*-declaration — a behavior change with no criterion at all. It leaves a sibling gap open: an agent can dodge coverage by declaring a criterion so vague it plausibly maps to the changed hunk. Coverage sees *a* criterion and stays silent; `/flow:verify-build` then judges the vague criterion PASS against equally vague narration. The two compose to bless a change whose only declared bar is untestably vague — the FB-0047/0048 self-attestation escape, one level up: you can't show a criterion green without a PASS, but you *can* author one so empty that PASS means nothing. Flagged as a named roadmap item at PR-2's own staff-review push-further pass; this PR builds it as specified.

**Design decisions.**
- **Deterministic, never an LLM judgment.** The orchestrator's brief was explicit: a downstream bounded-retry loop needs a mechanical signal to retry against, and judge prose is reward-hackable. A regex heuristic over the extracted criterion text, not a subagent call.
- **Lives in verify-build, not coverage.** The roadmap entry was explicit this is criterion *quality*, verify-build's axis — not criterion *presence*, coverage's axis. Confirmed at the plan gate by reading `audit-coverage/SKILL.md`: it is an LLM-judged fork (`agent: auditor`) checking whether a criterion exists; adding a keyword heuristic there would blur two different kinds of check into one skill.
- **Reuses the `no_plan_fallback` integration shape exactly.** `findings-schema.json` already had a precedent for "a Step-3-derived signal surfaced through `metadata` for `/flow:ship` Step 2 to convert into a manifest entry" (`metadata.no_plan_fallback`). `vacuous_criteria_found` is the same shape, confirmed by reading every `add-entry` call site in the repo (all live in `ship/SKILL.md`, including `toolchain`'s, whose underlying finding originates in a different skill entirely) — manifest writes are centralized in one place by convention, and this follows it rather than inventing a new pattern.
- **Reuses the `declare + fence` verb rather than adding a new one to the closed `VERBS` vocabulary.** The verb only changes classification behavior for `security`/`a11y`/`visual-deliverable`/`toolchain`; for a plain `ask` kind it's inert, so a new verb would be unused vocabulary surface for no behavioral difference. Orchestrator-confirmed at the open-call review.

**Technical decisions / tradeoffs.**
- **Precision over recall, explicitly.** The heuristic is `VACUOUS_PREDICATE_RE` (a small closed vocabulary of generic success verbs, end-anchored to the criterion's trailing clause) AND NOT `CONCRETE_SIGNAL_RE` (a broad escape hatch — any digit, quoted/backticked literal, arrow, or named-observable verb/noun anywhere in the string suppresses the flag). A missed vacuous criterion is an accepted residual; a false `[decision-required]` on a genuinely specific criterion is what gets a gate routed around and stops protecting anything. Documented residual false negatives: "Works differently than before" (real trailing detail defeats the end-anchor — correctly judged more specific than bare "works"), "Error handling works as expected" (contains "error," an escape-hatch word, even though "error handling" alone names no specific error/path).
- **walk-pin-lint.py does not already cover this — confirmed by full read, not assumed.** `skills/critique-plan/lib/walk-pin-lint.py` (FB-0068, SHIPPED) asks, at plan-critique time over the whole plan document, "does this checkbox name a verification *method*" (a test id, or a pin-marker + artifact noun). This new script asks, at extraction time over the active Spec-walk block only, "does the criterion's own text name an observable predicate." They compose rather than overlap, proven with a counter-example each direction: `"Rate limiting works correctly → verify: manual QA"` is PINNED (walk-pin-lint passes) but still VACUOUS (this check fires); `"Retries back off exponentially, capped at 5 attempts"` is UNPINNED (walk-pin-lint flags it) but NOT vacuous (this check does not fire). Recorded in `docs/workflow.md` § 10 so the next reader doesn't re-litigate it.
- **`docs/workflow.md` gets a sentence, not a dedicated paragraph.** Open call at the plan gate, resolved at execution by checking the actual doc: of the 9 pre-existing `KIND_COPY` kinds, only `coverage` and `toolchain` get individual dedicated prose there — the other 7 are covered by the manifest mechanism being explained once, not per-kind. `vacuous-criterion` matches that pattern: one sentence next to `coverage`'s paragraph (its direct sibling), not a new section.

**Lessons learned — the one worth keeping.** `/flow:critique-plan`, run on this plan before execution, caught that the first draft's own eval fixture was itself an instance of the exact defect this checker exists to catch. The plan listed five "worked negatives" — criteria the heuristic must NOT flag — as proof the escape hatch (`CONCRETE_SIGNAL_RE`) worked. None of the five actually exercised it: the vacuous-predicate regex never matched any of them in the first place (none of their trailing clauses were "works"/"correctly"/etc.), so they were correctly unflagged by construction, not by the AND-NOT mechanism the plan credited. **A vacuous test, inside a vacuous-criterion checker's own fixtures** — five different reasons for the same right answer, indistinguishable in a pass/fail table, none of them the reason claimed. Fixed by adding the one case that actually reaches the branch: `"Returns a session token and works correctly"` — its trailing clause DOES match the vacuous-predicate regex, and it is unflagged only because the escape hatch also fires. The eval harness (`run_criterion_specificity_evals.py`) asserts this case explicitly, by name, separate from the general fixture pass, rather than letting it dissolve into the flagged/unflagged set where the distinction would be invisible again. Generalizes beyond this script: any predicate built as `A AND NOT B` needs at least one fixture where `A` is true and `B` is what saves it — not only fixtures where `A` is false. Synthesized as FB-0104 alongside the escalation-boundary lesson from the same session (whether an open call changes what SHIPS is what decides if it routes to a human, not the mere existence of ambiguity).

**Lessons learned #2 — the flagship counter-example was empirically false, and reading the code is not the same as running it.** `/flow:staff-review`'s staff-engineer lens re-ran the exact counter-example this PR's own docstring, history entry, and `docs/workflow.md` cite as proof the check composes with `walk-pin-lint.py` rather than overlapping it — `"Rate limiting works correctly → verify: manual QA"` — and got `"vacuous": []`. Not flagged. **BLOCKER.** Root cause, in two layers: (1) the first draft's `_CONCRETE_SIGNAL_RE` escape hatch included the pin-marker arrow itself, reasoning "an arrow points at a concrete artifact" — but this repo's own Spec-walk convention puts the arrow *after* the claim, as a verification-method annotation, not inside it; (2) independent of that, the end-anchored `_VACUOUS_PREDICATE_RE` design assumed the vacuous phrase is the criterion's trailing clause — an assumption a pin suffix always breaks, since the pin annotation becomes the new trailing clause. **Every pinned criterion in this repo — which is all of them; every Spec-walk checkbox in this very PR ends in `→ verify: ...` — was structurally unflaggable, regardless of vagueness.** This is not one of the documented residual false negatives; it swallowed the checker's entire real-world target population, undetected because the eval fixture (`mixed.json`) contained zero pin-marked cases. Fixed by stripping the pin-marker suffix (mirroring, not importing, `walk-pin-lint.py`'s `PIN_MARKERS` vocabulary — that script has no shared-library shape) before either regex runs, so the heuristic judges the CLAIM, never the verification method appended after it — the same claim/method split `walk-pin-lint.py` already draws, now actually enforced instead of merely asserted in prose. The fix itself needed two iterations: the first stripping regex used a `\b` immediately after `→`/`->`, which never matches (neither a non-word arrow character nor the following whitespace is a word character, so `\b` has no boundary to find there) — caught by re-running the flagship example a second time after the "fix" still didn't flag it, not by re-reading the regex. Two new fixture cases pin both directions explicitly (`test_pin_marker_interaction`): a pinned-but-vacuous criterion must still flag, and pinning must not itself manufacture a false positive on an already-specific one. **The generalizable lesson, on top of the one from critique-plan above: a documented counter-example is a claim, not a proof, until someone actually executes it.** This PR's own machinery was validated by the exact bug class it targets **four separate times**, and none should get compressed out: (1) critique-plan caught the first draft's eval fixture never exercising the AND-NOT branch it claimed to prove — a vacuous test inside a vacuous-criterion checker; (2) staff-review caught the flagship documented counter-example silently failing — the vacuous-criterion detector defeated by exactly the kind of escape hatch (a pin marker) it exists to close; (3) even the FIX for (2) needed a second pass — the first stripping regex's `\b` after a non-word arrow character never matches, so the "fix" still didn't flag the counter-example, caught only by re-running it a second time, not by re-reading the regex; (4) at the security-decision resolution, the first fix for the shell-injection finding (a quoted heredoc) was itself reasoned-but-unexecuted — a fresh adversarial re-verification pass, followed by an actual empirical reproduction (`touch /tmp/INJECTED_PROOF` genuinely ran via a crafted criterion containing a line equal to the heredoc's own fixed delimiter), showed the "fix" traded one injection vector for a narrower one. Four layers (plan-critique on prose, staff-review on shipped code, self-check on a fix-in-progress, adversarial re-verification on a security fix), same root failure every time: something read as verified because it was reasoned about and written down, not because it was executed. The final fix (capture via the Write tool into a file, reference via `"$(cat ...)"`) was itself empirically tested against the exact payload that broke the heredoc version, plus a fake-closing-quote-and-semicolon payload, before being trusted.

**Also from staff-review — 3 copy NITs (fixed) + 1 follow-up (routed to roadmap § Exploration).** The UX-designer lens compared the new `KIND_COPY["vacuous-criterion"]` entry against its 9 siblings and found: the `why` field named a sibling kind (`coverage`) by internal identifier — exactly the "engineer shorthand" the table's own doc comment says these fields exist to eliminate; `waive_cost` was phrased two abstraction levels removed from its siblings' concrete-consequence pattern; and "acceptance criterion" (this entry) vs. "test criterion" (`coverage`'s) drifted terminology between two kinds presented everywhere else as a matched pair. All three fixed in place. A fourth finding — the rendered finding line quotes the vague criterion verbatim with no framing, momentarily reading as an assertion rather than a flagged problem — fixed by prefixing the `ship/SKILL.md` producer template with `Declared criterion (too vague): "..."`. The push-further lens's one inline-cheap finding (the flagged reason was a canned generic string regardless of which phrase actually matched) was folded into the BLOCKER fix above — `is_vacuous` now interpolates the actual matched phrase. The UX lens's FOLLOW-UP (no copy-consistency lint exists over `KIND_COPY`, so this class of drift will recur at the next kind addition) is real but not a one-line fix — routed to `roadmap.md` § Exploration rather than built here.

**Also from security-review — a decision-required finding, resolved by the human at the ship gate, fixed per-site (and the first fix attempt was itself caught incomplete).** The new `[vacuous-criterion]` producer bullet in `ship/SKILL.md` instructed the agent to embed the (untrusted, plan-author-controlled) criterion text verbatim inside a double-quoted shell argument when composing the `add-entry --finding "..."` command. Since `criterion-specificity.py`'s own escape hatch treats backticks and quotes as *positive* specificity signals, a well-formed criterion is expected to contain them — so an embedded `"` breaking out of the intended shell string was the common case, not an edge case. The same nested-quote shape already existed at the pre-existing `status-surface` producer site, so this PR added a **second** instance of the class rather than a wholly new one. Three candidates were offered: (a) a narrow prose fix scoped to just this PR's new bullet; (b) a systemic interface fix — `add-entry` reading `--finding`/`--resolution` from a file/stdin instead of a raw shell argument — across all ~10 producer sites; (c) accept the risk as-is.

**First attempt at (a) — a quoted heredoc (`<<'FLOWEOF'`) capturing the criterion into a variable — closed the quote/backtick/`$()` vector but opened a narrower one, caught by a dedicated adversarial re-verification pass (not self-graded).** Bash heredocs terminate on the first line that exactly equals the delimiter, regardless of what the delimiter appears inside — so a criterion containing a line literally reading `FLOWEOF` ends the heredoc early and hands everything after it to the shell as ordinary commands. Reproduced empirically (`touch /tmp/INJECTED_PROOF` genuinely executed via a crafted criterion body). **Final fix: capture the criterion text via the Write tool into a scratch file (no shell parsing of the content at all — there is no delimiter for anything to collide with), then reference it via a double-quoted command substitution (`"$(cat "$SCRATCH")"`)** — the same safety property `"$VAR"` and `jq -n --arg` both rely on, applied through a channel with no text-based boundary at all rather than one that's merely harder to hit. Verified against both the delimiter-collision payload that broke the heredoc version and a second payload (a fake closing quote + `;` + trailing command) crafted specifically to probe the new construction.

**Human decision: (a), with (b) dispatched separately as a fast follow that supersedes it.** (c) was explicitly ruled out, and the reasoning is worth keeping: this PR's own framing was that it "adds a second instance of a pre-existing class" — and knowingly propagating a shape just identified as unsafe is precisely how a class spreads. Two instances is a coincidence; a third would be a pattern, which is the exact fan-out failure `.claude/rules/general.md` § Consistency discipline exists to stop before it compounds. Fixed by capturing the untrusted criterion text through a quoted heredoc (`<<'FLOWEOF'`, not `<<FLOWEOF` — the quoting is what stops `` ` ``/`$()`/`"` inside the heredoc body from being re-parsed as shell syntax) into a variable, then referencing it via `"$FINDING"` rather than splicing it into the command text — the same two-step "capture soundly, then reference safely" shape the audit-skips stamp construction already uses in this file (`jq -n --arg`), adapted from building a JSON value to building a CLI argument. Scoped to only the `vacuous-criterion` bullet this PR added; the other ~9 pre-existing sites (including `status-surface`) still carry the shape and are NOT touched here — that is the systemic fix (b), tracked as its own roadmap § Next item and dispatched to a separate worker. This PR's fix is deliberately a stopgap for the one site it introduced, not a partial attempt at the interface-level fix — the next reader should not mistake the narrow fix for an abandoned wider one.
