## 2026-09-04 — Spike: AGENTS.md vs skill-shaped packaging — is flow's architecture wrong?

**Branch:** `conductor/spike-agentsmd-vs-skills-packaging-evals` · **PR:** (assigned at open) · **Mode:** spike · **Version:** v1.37.0 unchanged (zero `plugins/flow/**` files touched — docs-only diff: `dev-docs/research/2026-09-agents-md-vs-skills.md` new + one `dev-docs/README.md` index row)

**Research question.** Flow ships 22 skills and 10 agents; its entire delivery mechanism is skill-shaped. Vercel published *"AGENTS.md outperforms skills in our agent evals."* Is flow's packaging wrong — should the guidance move to a passive AGENTS.md/CLAUDE.md payload?

**What was built.** No code. `dev-docs/research/2026-09-agents-md-vs-skills.md` (~460 lines) — every primary source fetched live and quoted from the fetched bytes (the Vercel results figure downloaded and read as an image, not inferred from prose), repo facts measured at HEAD with `tools/harness_audit/harness_audit.py --surfaces` and `git grep`, plus **three experiments (E1–E3) that were human-approved and executed** rather than reasoned about. Indexed in `dev-docs/README.md` in the same commit per the repo rule.

**What we learned.**

*On the packaging question — the answer is no, change nothing, and the headline does not survive its own evidence.*
- **Vercel's published results figure contradicts its published tables**, in the same post, under the caption presenting it as the result. The figure shows **n=11 tasks, run-1 only**, and a **SKILL arm that BEATS baseline** (10/11/10 vs 9/11/9 on build/test) — while the tables say the skill tied on pass rate and lost on tests (58% vs 63%). The post never reconciles them. An independent HN reader read the same screenshots the same way (29/33 vs 33/33), so both readings agree; the gap is 1–2 tasks wide.
- **The winning artifact is a `CLAUDE.md`, not an AGENTS.md** — confirmed in the figure's column header *and* in the shipped codemod source (`injectIntoClaudeMd`, `targetFile || 'CLAUDE.md'`). The arms differed in **≥3 ways at once**, including an anti-pretraining instruction (`Prefer retrieval-led reasoning…`) only the winner received; the losing skill was never published, so "bad description" — the single most likely cause per both OpenAI's and Anthropic's first-party guidance — cannot be ruled out.
- **The larger measured result runs the other way.** SkillsBench (arXiv 2602.12670v4; 87 tasks × 18 configs × 3 trials = **9,396 trajectories**) measures curated skills at **+16.6 pp**, invocation **46.4–99.2%** by harness, and states *"Skill discovery is usually not the bottleneck."* **Nobody has replicated Vercel's actual comparison** — SkillsBench has no passive arm, Vercel's own OSS harness has no skill arm.
- **Correctly scoped, the finding lands on 1 of flow's 22 skills** (`log-disagreement`, the only genuinely model-invoked surface). **12 are user-invoked commands** — the exact case Vercel's own conclusion carves out (*"vertical, action-specific workflows that users explicitly trigger"*) — and **6 more are reached programmatically** via `Skill()` from another skill's body. Flow already made the "remove the decision point" move the post recommends.

*On loading — the valuable part; two of three experiments returned defects.*
- **E1 (RESULT):** `paths:` frontmatter on a `SKILL.md` **does not activate the skill**, at either project or plugin scope, in Claude Code v2.1.257. Therefore flow's four rule-skills (`general`, `plan-discipline`, `documentation`, `exploration`) **have not loaded for any consumer since Phase 00 shipped in v1.33.0**. Measured in 3 fresh sessions, 3 independent instruments (`InstructionsLoaded` hook, transcript content search, agent self-report), with positive controls (`.claude/rules/*.md` path-scoped rules) firing on the same Reads in the same sessions. Isolated with a throwaway project-scoped probe skill, so it is neither a plugin-scope nor a glob-syntax problem. This is the **third instance of the FB-0085 class and the second created by Phase 00 itself**: Phase 00 fixed a never-loading feature by moving it to a different never-loading mechanism, and verified *registration* instead of *activation*.
- **E2 (INCONCLUSIVE, reported as such — not estimated):** `log-disagreement`'s write path verified working end-to-end; the one drain on record (#119) captured 41 queued lessons vs 1 disagreement record, and `DISAGREE.md` has never had an entry — but there is **no denominator**, and the real store is machine-local on the user's Mac, unreachable from this cloud workspace. A suggestive ratio, not a rate. Do not tune the description before measuring.
- **E3 (RESULT):** `exploration`'s globs (`src|app|lib|packages/**`) match **0 files** in `health-tracker` (0/515), `ripe` (0/98), `music-app` (0/92), and **0 in flow's own repo**; only `portfolio` matches (56/237). E1 makes this moot today, but it means the fix is two-part — fixing activation alone leaves `exploration` dead in 75% of the fleet.

*Incidental first-party confirmations.* `claude plugin details flow@flow` reports **~4,645 always-on tokens** for the current build, up from ~4,122 at v1.29.0 (**+13% across seven releases**) — a real measured growth trend feeding roadmap item AB. And probe 2 saw 21 of 22 skills, with `post-merge` correctly hidden by `disable-model-invocation`, confirming the §2.4 context-cost model behaviorally.

**Recommendation: proceed — change no packaging; fix the loading.**
- **No repackaging.** Nothing in the evidence clears FB-0088's deliberately-high bar for new machinery. Flow's 478,587 chars of Class B skill bodies are arithmetic, not preference, and SkillsBench Finding 6 measures ≥4 concurrent skills as the *worse* direction (+10.1 pp vs +19.0 pp for 2–3).
- **Next real PR is S0** (routed to roadmap § Now): restore path-activation for the four rule-skills, picking option (a) confirm-and-report-upstream / (b) ship as `.claude/rules/*.md` via the template / (c) accept model-invocation with earned descriptions — a human decision at the plan gate, because option (a) depends on upstream behavior this spike could only observe from outside. `/flow:doctor` Check 3.2 must be upgraded from "registered" to "activates" in the same PR.

**Design decisions.**
- **Read the image, not the prose.** The single most decision-relevant fact — the figure contradicting the tables at n=11 — was invisible to every prior citation in flow's corpus because nobody had downloaded and read the results screenshot. The spike treats the fetched bytes, not the surrounding narrative, as the source.
- **Ran the experiments instead of predicting them.** The draft §6 recommendation was written from documentation alone; E1–E3 were then run and **changed it** — the draft's "unmeasured loading assumptions" became one hard defect (E1), one two-part defect (E3), and one honestly-inconclusive (E2). Per `.claude/rules/documentation.md` § "Recorded rejections," an unmeasured prediction may not close a question; the spike measured rather than asserted.
- **Scoped the finding by surface class, not by headline.** Flow's 22 skills split into four loading modes (§4.1); the AGENTS.md finding applies only to the one genuinely ambient-invoked surface. Answering "is flow's architecture wrong?" required separating "who decides to load" from "when the cost is paid," which the AGENTS.md-vs-skills framing collapses.

**Technical decisions.**
- **The `paths:` guardrail is the single most load-bearing line in the doc.** The most likely wrong turn on S0 is to "fix" it by deleting the `paths:` fields — the FB-0077 shape (a prohibition satisfiable by deletion; `.claude/rules/general.md` § Consistency discipline). Removing `paths:` makes every symptom vanish and leaves the four rules loading exactly as often as now: never. Whatever option lands **must pair the change with a positive assertion that the four rules reach context**, not merely that nothing is misconfigured.
- **Routed, did not fix — this is a spike.** Two live bugs are routed to their own PRs: S0 (roadmap § Now) and a `harness_audit.py:157` misclassification (roadmap AB Step 1b) that hardcodes the 85,176-char `plugins/flow/docs/workflow.md` as always-loaded when nothing loads it — **64% of AB's reported Class A total, making its headline always-loaded figure ~3× too high.** That second one is a live bug in already-merged code (#136), recorded durably so AB Step 3 does not inherit the misclassification when it builds the real token-count report.

**Tradeoffs discussed.**
- **Recommending "change nothing" on packaging was the point, not a cop-out.** The bar (FB-0088; ~91 queued roadmap items, a recent review that found real overbuilding) is deliberately high. The evidence that *would* have justified repackaging — a large, controlled, replicated passive-vs-invocable comparison on *procedural* content — does not exist; all published evidence is on *factual* content, at n=11, with the losing arm withheld. The flip condition is stated in §6b: a controlled replication with n in the hundreds on procedural content.
- **E2 left inconclusive rather than filled with an estimate.** A fabricated capture-rate would have been worse than an honest "no denominator" — tuning `log-disagreement`'s description against a made-up number is the exact silent-degradation class the spike exists to catch. Routed to § Exploration with its surfacing trigger (a seat with machine access, or the next `/flow:contribute` drain).

**Lessons learned.**
- **What is registered is not always what is running** — the finding, applied to the spike's own conduct. The research session uninstalled/reinstalled the flow plugin mid-session to get off a stale cached v1.29.0 build (pre-Phase-00, which would have confounded E1); that silently broke *its own* skill/agent registry — `/flow:ship-spike` stopped resolving in that session, which is why this handoff-to-a-fresh-session exists at all. Same class as E1's finding: a plugin can be present-on-disk, or registered-with-the-loader, or actually-activating, and those are three different facts that a check verifying only the cheaper one inherits the bug it was built to catch (Check 3.2 verifies registration; E1 measured activation false).

**Disposability:** the research doc is **kept** — it is the deliverable, and it gates the next PR (S0). No code was written, so nothing to delete. The two routed bugs (S0, AB Step 1b misclassification) each get their own follow-up PR.
