# v1.53.0 — the four rule-skills, and a measurement that refused the answer it was built to find

> **S0 closes as WITHDRAWN, not fixed.** The four rules still do not load for consumers.
> Rewriting their descriptions changed nothing at plugin scope — **0/3 before, 0/3 after, 0/2 on the
> default model**, across 52 probe sessions. Ben decided (2026-09-29) that S0 closes at *honest*: the
> advertised auto-loading is **withdrawn** rather than restored, the four rules nudge rather than
> enforce, and every shipped doc now says so. Restoring enforcement needs the `SessionStart` hook,
> recorded in the roadmap with its per-session cost and deliberately not built.

**S0 / FB-0124.** Ben chose option **(c)** at the human gate: stop trying to make the four rule-skills
path-activate, and let Claude load them by judgment from their descriptions. That shipped. What also
shipped is the measurement, and **the measurement did not support the premise** — see § "What the numbers
actually said".

## The four rule-skills are now model-invoked, honestly labelled

`general`, `plan-discipline`, `documentation`, `exploration` each get a rewritten `description` plus a new
`when_to_use` naming trigger *moments* rather than file *paths*. `paths:` is gone from all four.
`user-invocable: false` stays (its documented row is exactly the shape wanted: *"Description always in
context, full skill loads when invoked"*). `disable-model-invocation` is deliberately **not** set — its row
reads *"Description not in context"*, which would forbid the one path that works.

**Two doc corrections behind this, both verified against the primary sources:**

- **`paths:` on a `SKILL.md` is a real, documented field — not a bug, and there was nothing to report
  upstream.** It *limits* an activation the `description` otherwise earns: *"Glob patterns that **limit**
  when this skill is activated… Uses the same **format** as path-specific rules"* — format, not semantics.
  The read-trigger semantics we had assumed belong to `.claude/rules/*.md`. Two mechanisms, one field name.
- **A plugin cannot ship rules at all.** `rules/` is not in the plugin standard layout, and the same page
  says outright: *"To include instructions that load into Claude's context, put them in a skill."* That is
  the docs endorsing this mechanism, not merely lacking an alternative.

## `/flow:doctor` stops reporting `[PASS]` over a claim it cannot check

Check 3.2 asserted the four *"auto-load on path matches"* and tested it by grepping
`claude plugin details` for the four **names**. That measures **registration**, not **activation** — and it
stayed green for twenty releases. It now asserts registration (labelled as such) plus the frontmatter
contract that makes model invocation possible, each negative paired with a positive so deleting a skill
fails rather than passes.

**New `[UNCHECKED]` marker class.** Activation is a model-judgment event inside a session; no shell
observes one. So Check 3.2 says that in its own output rather than implying a clean bill of health
(FB-0121). `[UNCHECKED]` sits **outside** the verdict arithmetic — routing it to `[WARN]` would put every
consumer permanently below `[READY]` over an item nobody can clear — and the count prints **inline** on the
verdict line, `[READY] (2 unchecked)`, so the unseen items stay visible. Two rules keep the class from
becoming a drawer: every `[UNCHECKED]` line must name the mechanism that would make it checkable, and that
clause is the line's own deletion criterion.

## A regression this PR would have shipped, caught by `/flow:critique-plan`

`plugin-provenance.py`'s `_is_rule_skill()` keyed on `paths:`. Removing `paths:` would have silently
reclassified all four as command skills, printing *"a model asked to run one would wrongly conclude it does
not exist"* — which that function's own docstring calls "something simply untrue of it". CI could not catch
it: the eval pinned the classifier to a **synthetic** `a-rule` fixture that carried `paths:`, so the
fixture kept passing after the real files stopped having the shape. Re-based on `user-invocable: false`,
and the eval now asserts the classifier over the **four real files** plus a real command skill — both
halves, so neither a hardwired `True` nor a hardwired `False` can pass.

## Nine false claims corrected — one of them write-once

`README.md`, `docs/automation-boundaries.md`, `docs/first-pr.md` ×2, `plugins/flow/docs/workflow.md`,
`plugins/flow/skills/spawn/SKILL.md`, `doctor/SKILL.md` ×3. And **`template/base/CLAUDE.md.template` still
pointed at `${CLAUDE_PLUGIN_ROOT}/rules/`** — the directory Phase 00 deleted in v1.33.0. `bootstrap.sh`
copies that file into every consumer repo, so it is the one surface flow **cannot reach again after
install**: a wrong line there is wrong forever in every project that adopted flow. That block now
describes both mechanisms and says which one is actually load-bearing (yours, not the plugin's).

Also retired as moot: roadmap **S2** (`exploration`'s globs reach 1 of 4 consumer repos) and
**config-driven `paths:`** — with no globs there is nothing to widen and nothing to configure. Both kept
struck-through, because the measurement behind S2 is the argument against ever re-introducing a hardcoded
source-root glob.
