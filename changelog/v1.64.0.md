## v1.64.0 — `/flow:ship` reads CI before it says "ready"

**The headline.** `/flow:ship` no longer calls a PR ready that GitHub would block. Until now every
readiness signal the pipeline produced read an artifact *this session* wrote — a green local sweep is
not CI. Measured on #176: six consecutive red CI runs, every flow gate green, the manifest `READY`,
the body saying "ready", and GitHub reporting the PR `BLOCKED`. Nothing looked, so nothing
contradicted it.

- **CI is now a sixth ship-readiness condition, with three states — and the third is the one that
  matters.** `passing` → may be ready. `failing` → draft, **naming the failing check**. **`pending` →
  "checks pending", never ready.** Treating "nothing has failed yet" as "everything passed" is the
  cheapest implementation and it is the bug.
- **Waiting costs no tokens.** The gate blocks on `timeout <ciWaitSeconds> gh pr checks --watch`
  rather than polling in an agent loop: the process sleeps, the model does not think. On timeout it
  reports `pending` honestly and never upgrades it to a pass.
- **`gh` absent, unauthenticated, or erroring → "CI status unknown", never ready.** Projects without
  GitHub are not broken: the gate degrades loudly with a `⚠️` and a draft, and never halts the
  pipeline.
- **"No checks reported" is two different worlds, and flow now tells them apart.** An empty check list
  with GitHub reporting `CLEAN` means nothing is configured or required — the condition is satisfied,
  with its reason stated. An empty list on a PR GitHub reports as `BLOCKED`/`DIRTY`/`BEHIND` is a
  blind spot, not a clean bill of health.
- **Non-Actions CI is seen.** CircleCI, Buildkite and anything else reporting a commit status arrives
  as a different node type in GitHub's rollup and is mapped, rather than reading as "no checks".
- **Three new draft-manifest kinds** — `ci-failing`, `ci-pending`, `ci-unknown` — each with its own
  plain-language explanation of what did not pass. All three are check-only: a human's assertion never
  clears them, so **the PR stays a draft until a check is actually observed passing**. If you accept
  the risk, you mark it ready yourself.
- **The whole Step 8 predicate is now a script, not a memory.** `skills/ship/lib/ship-readiness.py`
  evaluates all six conditions and **names which one did not pass**. Two of them have no artifact to
  read yet, and it says so (`UNDECLARED`) rather than assuming they are fine — `UNDECLARED` is never a
  pass.
- **`/flow:ship-spike`** reports all three CI states in its hand-off and converts to a draft only on a
  red check — spike PRs keep the halt-and-adjudicate shape they already had for the other two.
- **New `ciWaitSeconds` config slot** (schema 38 → 39 slots), default `600`, `0` to read once without
  waiting. CI duration is project-shaped: flow's own suite settles in ~75s, a large one can take 20
  minutes.

**Known limitation.** GitHub only runs `pull_request` checks once a PR exists, so the gate necessarily
runs just *after* the PR is created and converts it to a draft if CI is not green. The window is
bounded within that one step and closes before the PR is handed to you — but someone watching GitHub
inside it would briefly see a non-draft PR.

**Breaking changes:** none. Schema grows to 39 slots; every existing config resolves exactly as
before. A project with no CI, or no `gh`, keeps working — it gets a loud warning and a draft instead of
a false "ready".
