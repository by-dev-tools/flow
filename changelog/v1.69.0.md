## v1.69.0 — `/flow:retro` closes out a whole batch, and you can just ask for it

**The headline.** After you merge a batch of PRs, one command closes them all out. Before, `/flow:retro`
took exactly one PR number, so nine merges meant nine runs — nine prompts, nine `docs: land` PRs editing
the same roadmap lines, nine feedback passes. Now `/flow:retro 151 153 154` handles those three together,
and a bare `/flow:retro` takes every PR merged into the default branch since the last retro and just does
it, with no confirmation prompt.

- **Shared steps run once, per-PR steps run per PR.** One doc-currency PR for the whole group (`/flow:land`
  now accepts a list and opens one `docs: land #151 #153 #154` PR), one feedback synthesis, one verdict that
  lists every PR. The merge check and the branch cleanup stay per PR. A PR that was closed without merging,
  or is still sitting in a merge queue, is named in the verdict and left out of the rest — it no longer
  aborts the group. One poll budget covers the whole group, not one per PR.
- **"Since the last retro" is a per-repo watermark.** Kept beside the harvest marker
  (`…/contributions/last_retro.json`), keyed by repo, and only moved by a no-argument run whose docs all
  reconciled. The first run in a repo looks back 7 days and takes at most 20 PRs, and says so if it
  truncated. `docs: land` PRs are never picked up as input — they are the output of the previous retro.
- **Branch cleanup learned from a real batch.** Squash-merged branches make `git branch -d` refuse every
  time, so the skill no longer treats that as a surprise: it reports each such branch as left behind (and
  whether its tip is the merged head) instead of force-deleting. The remote branch is deleted only when its
  tip still equals the PR's `headRefOid` — a push after the merge keeps it. A branch checked out in another
  worktree is skipped and named. A merged branch that is the base of another open PR is left alone and the
  dependent is named. Fork PRs are still never touched; `git branch -D` is still never used.
- **You can ask for it in chat.** `/flow:retro` was `disable-model-invocation: true`, which meant "run the
  retro" in a conversation got a refused call and you had to type the slash command. It is now
  model-invocable, with an AUTO-INVOCATION clause like `/flow:ship`'s: the agent may run it when you ask for a
  retro or tell it PRs have merged, never mid-loop ahead of a merge. The safety is the same gate that was
  already underneath: §2 refuses every PR that is not merged, and nothing in the skill can merge.
- **Stacked PRs are documented, in one place.** When one PR depends on another open PR, `docs/workflow.md`
  now says to open it as a GitHub Stacked PR (`gh stack`) based on its parent's branch and merge bottom-up,
  instead of independent PRs that later need conflict-resolving merges. `/flow:ship`'s PR step carries a
  one-line pointer. The commands were checked against the `github/gh-stack` README, not run.

**Not done, deliberately.** The review skills (`/flow:security-review`, `/flow:accessibility-review`,
`/flow:staff-review`, `/flow:ship`) still read the session's own working directory, so an orchestrator
cannot point them at a PR checked out in another worktree. Giving them a target touches dozens of diff
sites and the argument-safety rules, which is not a small change; it is queued in `dev-docs/roadmap.md`.

**Breaking changes:** none for callers. `/flow:retro` with a single PR number behaves as before. The one
visible difference is that a bare `/flow:retro` no longer asks which PR you mean — it takes the group.
`/flow:land` with one number is unchanged.
