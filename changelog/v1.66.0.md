## v1.66.0 — `/flow:audit-skips` can find its own checker when flow is installed

**The headline.** If you installed flow rather than cloning it, `/flow:audit-skips` has been reporting
`stamp_unverifiable` on **every single run** — a gate that could never look, telling you so politely
enough that nobody read it as a bug. Reported from the field against 1.29.0; reproduced on 1.64.0.

- **The fallback was never a fallback.** The skill resolved its stamp checker and its engine as
  `$CLAUDE_PLUGIN_ROOT/...`, else `plugins/flow/...`. That second path is *flow-repo-relative* — in your
  project it cannot exist. So whenever the host variable was absent there was no arm left, and **both**
  helpers went unreachable together, which is why the whole skill was dead against an install rather
  than merely unable to check a stamp.
- **Resolution now has three arms.** `$CLAUDE_PLUGIN_ROOT` (accepted only if it carries a plugin
  manifest) → the `installPath` in Claude Code's own `installed_plugins.json`, which names the *exact*
  version in use → the flow checkout, for flow's own development. Every candidate is identity-checked
  against its own `plugin.json` before anything is executed from it.
- **Not a cache glob.** A host can hold several cached versions, so `cache/*/flow/*/` can run one
  version's engine against another version's handoff. The install record is version-bearing and is the
  only *live* source, which is what a glob is not.
- **What the install record does NOT tell you.** It records what is installed *now*. A plugin update
  rewrites it immediately but needs a restart to take effect, so a session that began before an update
  keeps running the old copy while the record advertises the new one (flow measured this on itself:
  record 1.41.0, session still executing 1.29.0). Flow now says so where it reads the record, instead
  of claiming the record names the version in use — it doesn't.
- **"I could not verify" now names the real cause.** An unresolved plugin root says so, instead of
  reporting a helper missing from a leading-slash path that was never a location.
- **Still fail-closed, and nothing was ever waved through.** If no arm resolves, the output is the same
  refusal it always was — a gate that cannot look has never passed and still does not. So **no ship ever
  got a false clean pass from this.** But if you installed flow, the honest reading is that no PR's
  stage skips were ever actually audited; the gate refused, every time, and the refusal was quiet enough
  to look like nothing was wrong.
- **A successful run now says where it found flow.** The audit reports `plugin_root`,
  `plugin_root_arm` (`host-var` / `install-record` / `checkout`) and `plugin_root_ambiguous` alongside
  the stage verdicts. When a verdict looks wrong you can now tell whether the engine came from the host
  variable, the install record, or a local checkout — the question that was unanswerable for 35
  releases. If flow is installed more than once, the run says so instead of picking one silently.
- **A corrupt install record is now loud.** Previously an unparseable `installed_plugins.json` produced
  no candidates, no message, and a silent fall back to the local checkout.

**The belief that made this invisible for 35 releases.** Flow's own docs said `CLAUDE_PLUGIN_ROOT` is
always set inside a skill's `!`-block. Measured in one session: unset for `/flow:audit-skips`' fork,
set for `/flow:audit-plan`'s — both forked skills. Why it differs is not established, so the fix now
assumes neither. The bug was structurally invisible from flow's own checkout, where the broken arm is
the one that works — so the new regression cases run from a simulated **consumer** layout with no
`plugins/flow/` and the variable unset, and reverting the fix turns them red while the in-repo case
stays green.

**Known gap, not fixed here.** The same two-arm shape is in the other four forked skills.
`/flow:audit-plan` and `/flow:audit-completion` are worse: with no fallback at all, an absent variable
means the session extractor never runs and the reviewer audits an **empty context** — a reviewer that
cannot see, reporting no issues. Tracked in the flow repo's own feedback log as FB-0141 (`dev-docs/` is not shipped — see
https://github.com/by-dev-tools/flow).
