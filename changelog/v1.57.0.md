## v1.57.0

**The plugin auto-updater could only update installs that did not need updating — and the provenance row it feeds could be confidently wrong.** Dev-infrastructure fix plus one correction to shipped gate behaviour. (FB-0131)

- **`restart_pending` is now three-valued** in `skills/ship/lib/plugin-provenance.py`: `true`, `false`, or `null` when nothing available can tell. It was `bool(rv and reg_v and rv != reg_v)`, where `rv` is the PATH-pinned version — so on any host where that signal is unresolvable it returned `false` unconditionally and the restart-pending state was structurally undetectable while reporting as "not pending".
- **A "what ran" row read from the plugin registry can no longer claim `✓ matches this branch` when the reading is ambiguous.** `claude plugin update` rewrites the registry the instant it runs even though the update applies on *restart*, and it leaves the previous version tree on disk. Two trees in the plugin cache plus no run-pinned signal means nothing can say which one this process loaded — so the row names the registry as its source, says the session may still be running the older tree, and tells you how to check. **Measured:** in one session whose registered skill list never changed, the row moved from a correct `⚠️ NOT this branch, 26 releases back` to `1.55.0 ✓ matches this branch` the moment a currency hook updated the install. An agent read the tick and concluded the session's own honest warning was "pessimistic".
- **The tick is paired, not removed.** A genuinely PATH-pinned version that matches the branch still renders `✓ matches this branch`, and a single cached tree still reads as unambiguous — otherwise "never render a tick" would be satisfiable by deleting the tick.
- **New `cached_versions` field** in the JSON report, so the basis for the verdict is auditable rather than taken on trust.
- Also fixed in passing: the cache probe is confined to `~/.claude/plugins/cache`. Its first cut followed an `installPath` of `/nonexistent` and enumerated the root filesystem, reporting `bin, boot, dev, etc, …` as plugin versions.

**Known limitation, stated rather than discovered later:** flow ships no `bin/` directory, so the PATH signal this engine prefers resolves for flow on **no** host. Every flow reading is registry-sourced, and the cache-ambiguity probe above is what substitutes for it. See `dev-docs/roadmap.md`.

**Breaking changes:** none for consumers. `restart_pending` can now be `null` where it was previously always `false` on hosts without a PATH-resolvable plugin `bin/`; any consumer branching on it should treat `null` as "unknown", not as "no".
