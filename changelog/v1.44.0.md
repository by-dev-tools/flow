# v1.44.0

**SAFETY — a manifest entry can no longer close the manifest fence.**

`/flow:ship`'s NOT-READY manifest is delimited by an HTML-comment fence.
`extract_manifest_region` located the closing fence as a bare substring — the
first occurrence anywhere in the PR body — so an entry whose *finding text*
contained that marker truncated the region at itself and every entry after it
vanished from the parse.

Measured on the pre-fix tree: a body carrying one marker-bearing entry followed
by a real `[verify-build]` blocker parsed with the verify-build blocker
**absent**, and the coherence verdict moved `DECIDE` → `READY`. A pull request
whose behavioural gate had failed read as merge-ready.

**The fix:** both fences are matched **line-anchored**, splitting on `\n` only
(never `str.splitlines()`), and the region ends at the **last** line-anchored
close rather than the first.

All three properties are load-bearing, and two of them were added after a
staff-engineer review refuted the first version of this fix:

- `str.splitlines()` breaks on **eight** further code points (`\x0b \x0c \x1c
  \x1d \x1e \x85 \u2028 \u2029`). A finding carrying any of them around a bare
  marker still erased the `[verify-build]` blocker — measured, all eight. No
  write-time "newline collapse" strips `\u2028` or `\x0c`, so both layers missed
  them. `pr-coherence.py` already split on `\n`; this had diverged from an
  in-repo precedent that was correct.
- **Last close, not first.** A doc-style example quoting both markers on their
  own lines *above* the real manifest captured the region under first-close, and
  the real entries vanished — fewer entries, the unsafe direction.

**The same hazard existed one layer down and is fixed here too.** `parse_entries` consumed the
region and re-split it with `str.splitlines()` — so an entry whose *finding text* carried one of the
eight boundaries was split into fragments, matched no entry pattern, and was silently dropped.
Fixing the extractor alone left this reachable: the region was clean and its consumer re-broke it.
Found by the push-further lens after the extractor fix was already green.

**What this does not fix, stated plainly:** a finding that embeds a real `\n`
followed by a bare marker. That will be closed at write time by the newline
collapse the FB-0108 branch adds to `add-entry`; there is no write-time layer on
this branch, so the present tense would be a claim about absent code.

**Failure direction:** if the fences are not found line-anchored, the parser
returns the whole body — the same as "fences absent" — so it sees more candidate
entries, never fewer. A merge gate degrades toward not-ready.

Reachability: a latent self-trigger, one docs commit from live. `[status-surface]`
findings quote a verbatim line from a scanned candidate; none of the six defaults
carries the marker today, but `README.md` already discusses the manifest.

Regression cover: `run_manifest_triage_evals.py` gains a `[fence-injection]`
section — the attack, a prose quote of both markers, a control, the fail-safe
direction, all eight separators, the preceding-fence-pair case, an unclosed
fence, a CRLF body, and a paired positive asserting fence scoping still works
(without which "delete the fence" would satisfy every other assertion).

Mutation-tested against three builds: **12 failures** on the pre-fix tree, **8**
on a `splitlines()`-only build, green on the fix. The separator cases use a body
with **no real close fence** — with one present, the last-close rule rescues the
entry independently, so a closed-fence body passes even under `splitlines()` and
would not isolate the property it names. The first revision of this eval made
exactly that mistake and went green against the broken build.

FB-0109.
