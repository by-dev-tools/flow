ISSUE 1 · Undeclared change

Claim:
> "The overlay works correctly with no native `confirm`/`alert`/`prompt` calls (so it is safe to inject into any static page, including `file://`) → verify: grep the script for `confirm(`/`alert(`/`prompt(` and confirm none are present."

Hunk: `annotation-layer.html` — the `#an-wipe` handler (`if (!armed) { armed = true; this.textContent = "Delete all?"; ... armTimer = setTimeout(... 6000)`), the per-row `an-del` handler (`notes = notes.filter(...); save(); render()`), and the editor's `$("an-del")` handler. A reader can delete one comment from its panel row or from the editor, and delete every comment via a two-press "Delete all" → "Delete all?" control that re-disarms itself after six seconds of inactivity.

Why uncovered: I checked all thirteen criteria for any mention of deleting a comment. Criterion 9 is the closest — it constrains *how* a destructive confirmation may be implemented (no native `confirm`) and its verify step is a grep for `confirm(`, which passes on a build with no delete feature at all. Criterion 6 covers keeping a lost anchor rather than dropping it — the opposite of deliberate deletion. Nothing directs anyone to press Delete, Delete all, or the second press that actually destroys data, nor to discover that the arming state expires.

Suggested: Add a Spec-walk criterion for the delete paths, naming the two-press arm, the six-second auto-disarm, and that deletion persists across a reload.

ISSUE 2 · Undeclared change

Claim:
> "Clicking an element while commenting mode is on opens a comment editor pinned to that element → verify: manual click-through in a browser."

Hunk: `annotation-layer.html` — the capture-phase `keydown` handler (`if (e.shiftKey && (e.key === "ArrowDown" || ...)) { walkStep / walkDepth }`), `buildWalk()`/`walkStep()`/`walkDepth()`/`focusWalkTarget()`, the plain `ArrowUp`/`ArrowDown` widen/narrow branch, the `Enter` → `commit()` branch, the `focusin` listener that makes a Tab-focused element the pick target, and the `Escape` branch that calls `setCommenting(false)`. A keyboard-only reader can walk the page element-by-element with Shift+↑↓, widen/narrow the selection with Shift+←→, comment with Enter, and switch commenting off with Escape — and the on-page hint text advertises all of it.

Why uncovered: I checked criterion 1 (mouse click-through), criterion 3 (modifier-click passthrough — verifies the escape hatch, not keyboard targeting), and criterion 10 (screen-reader announcement scoped to "commenting mode toggles or the note count changes" — the walk's per-element `announce(descriptor(...) + " — press Enter to comment")` is neither). No criterion mentions a key, Tab, or keyboard reachability, so nothing would cause anyone to test the entire non-pointer path to creating a comment, including Escape silently turning the mode off.

Suggested: Add a criterion for the keyboard commenting path (Shift+arrow walk, Shift+←→ depth, Tab+Enter, Escape-to-off) with a keyboard-only manual check.

ISSUE 3 · Undeclared change

Claim:
> "Commenting mode persists across reloads via `localStorage` and defaults to on → verify: toggle off, reload, confirm state survives."

Hunk: `annotation-layer.html` — `#an-snap` and its handler (`snapPreview = !snapPreview; localStorage.setItem(PREF, ...)`), `drawHL(el, force)` gated on `snapPreview`, the `mousemove` listener that outlines the hovered element, and `flashHL()` (`flashT`/`fadeT`, the 460 ms/700 ms fade). With the preference on, an outline follows the cursor; with it off, the outline appears only on keyboard adjustment and as a post-commit flash of what was captured. The preference persists under its own key `flow-annotations-v2:snapPreview`.

Why uncovered: Criterion 2 is scoped to the *commenting* mode key and its verify step ("toggle off, reload") exercises only that switch; a build with no outline preview at all passes it. Criterion 11 covers light/dark appearance of "the floating control and comment panel," not whether a hover outline is drawn, suppressed, or flashed. No criterion mentions hovering, outlining, or a second persisted preference.

Suggested: Add a criterion for the hover-outline preference — default on, persists under its own key, and the post-commit flash that replaces it when off.

> "Notes survive a page re-render/regeneration by matching on content (heading + tag + role + text sample, or an author-supplied `data-pin-id`) rather than DOM index → verify: manual check across two renders of the same content."
