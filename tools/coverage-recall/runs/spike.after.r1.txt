ISSUE 1 · Undeclared change

Claim:
> "Clicking an element while commenting mode is on opens a comment editor pinned to that element → verify: manual click-through in a browser."

Hunk:
`annotation-layer.html`, the `keydown` capture handler plus `buildWalk`/`walkStep`/`walkDepth`/`focusWalkTarget` and the `focusin` handler — Shift+↑/↓ walks block-level elements, Shift+←/→ widens/narrows the target, ↑/↓ adjust a pointer-chosen target, Tab sets a target via `focusin`, and Enter commits a comment on the current target. A user can create a comment on any element without ever using a pointer.

Why uncovered:
Checked all thirteen criteria. Criterion 1 names clicking and verifies by "manual click-through". Criterion 3 covers modifier-click passthrough. Criterion 10 covers screen-reader *announcements* on mode toggle and count change, not keyboard targeting or commit. No criterion mentions a key, arrow, Tab, or Enter, so nothing would cause a tester to exercise the walk, the wrapper-skipping element list, the `targetFromPointer` guard that keeps plain arrows scrolling the page, or Enter-to-comment.

Suggested: Add a Spec-walk criterion for the keyboard path — e.g. "Shift+↑↓/←→ walks and widens/narrows the target and Enter comments on it; plain arrows still scroll the page → verify: manual keyboard-only pass over a prototype."
